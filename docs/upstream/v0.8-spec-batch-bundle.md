## P-02 — Verbatim SDRF/ISA Embed: `sample-metadata` Entity Type + `sdrf`/`isa` Data Kind

**Spec mechanism:** Adding a new Entity Type + Adding a new Data Kind
**Contract reference:** `docs/mzpeak-extension-contract.md §3.9`
**Source requirements:** SM-01, SM-02
**Implementing phase:** Phase 31 (embed), Phase 33 (ISA variant)
**Pending CURIEs:** `sample-metadata` entity-type term (tracked in `docs/cv-requests.md`)

### Proposed addition to spec `index.md`

```
### Entity Type: sample-metadata

A new controlled entity type for embedded sample-metadata files (SDRF TSV or ISA bundle).
Files registered with entity_type "sample-metadata" are discovery-addressable by controlled
term (rather than by filename alone).

#### Data Kind: sdrf

An SDRF (Sample and Data Relationship Format) TSV file embedded verbatim in the archive.
Archive member name: "sample_metadata/sdrf.tsv" (deterministic).

#### Data Kind: isa

An ISA-Tab or ISA-JSON file (investigation/study/assay) embedded verbatim.
Archive member names: "sample_metadata/isa/<basename>" (one per file; deterministic).

#### Authority rule

The canonical SDRF/ISA in the study repository is authoritative; the embedded copy is a
convenience denormalized projection. When they conflict, the repository copy wins (Q1, RATIFIED).
Readers MUST NOT reject an archive whose embedded copy has been superseded by a repository update.

#### Backward compatibility

Unknown entity_type already degrades to "other" in the current spec (existing readers still fetch
the bytes). Adding "sample-metadata" is additive; no breaking change.
```

## P-03 — `sample_list` Reuse + Run-Level Run→Sample Binding

**Spec mechanism:** File-Level Metadata JSON (`sample_list` — existing spec member)
**Contract reference:** `docs/mzpeak-extension-contract.md §3.11`
**Source requirements:** SM-05
**Implementing phase:** Phase 32
**Pending CURIEs:** none (reuses existing `sample_list` spec member)

### Proposed addition to spec `index.md`

```
### sample_list usage for SDRF-derived samples

When an SDRF or ISA bundle is embedded, the spec's existing `metadata.sample_list` member
is populated with one entry per distinct SDRF `source name` (or ISA Investigation source):

    {
      "id": "<slugified-source-name>",
      "name": "<verbatim source name>",
      "parameters": []   // lean projection (RATIFIED-G); characteristics live in verbatim blob
    }

Lean projection posture (Q9, RATIFIED): per-sample characteristics/factor_values are NOT
projected into `parameters` in v0.8 — the verbatim blob is the authoritative carrier.
The `parameters` array is emitted empty (`[]`) at v0.8; full characteristics projection is
deferred to ≥v0.9 (SM-07 deferred).

Run-filtered (v0.8.1): only the distinct source names whose rows match THIS run are projected
into `sample_list` — not the full study-wide sample set. The projection scope is recorded as
`metadata.sample_metadata.projection_scope: "run"`; the verbatim embedded blob retains full-study
fidelity. Row→run matching is by SDRF `comment[data file]` for SDRF and by ISA structural
assay→data-file linkage for ISA bundles (not filename-only).

### run_sample_binding shadow (metadata.study)

Until the native `ms_run.sample_ref` field (P-09) is merged upstream, run→sample binding
is recorded as `metadata.study.run_sample_binding` with `binding_provenance: "phase32_shadow"`.
This shadow binds one run to zero-or-more sample_list ids; its presence is contingent on a row
match (SDRF `comment[data file]` / ISA structural assay linkage) between the run and the embedded
metadata. A zero-match produces no binding (honest "samples mixed" default — SM-06).

Once P-09 is accepted and the writer merges, the shadow SHOULD be replaced by the native field.
```

## P-04 — [REFRAMED — RATIFIED-E] Samples-as-Channels via MS:1002602 + List-Valued `ms_run.sample_ref` — NO `channel_list`

> **Note:** the original P-04 (`channel_list`/`plex_id`/`channel_set`) is **DROPPED** (RATIFIED-E,
> 2026-06-09). This proposal is REFRAMED as the samples-as-channels model that replaces it.
> The §3.6 channel_list schema in the extension contract is preserved for provenance only and
> MUST NOT be implemented.

**Spec mechanism:** File-Level Metadata JSON (`sample_list`) + upstream `ms_run.sample_ref` schema field
**Contract reference:** `docs/mzpeak-extension-contract.md §3.12`
**Source requirements:** CHAN-01, CHAN-02
**Implementing phase:** Phase 34
**Pending CURIEs:** MS:1002602 ("sample label") is canonical PSI-MS — no new minting needed

### Proposed addition to spec `index.md`

```
### Isobaric / TMT / iTRAQ channels as labeled sample_list entries

For isobaric labeling experiments (TMT, iTRAQ, etc.), channels are represented as labeled
sample_list entries using MS:1002602 ("sample label") in `parameters`, rather than a separate
`channel_list` structure. Each param object has the shipped shape `{cv_ref, accession, name, value}`
(required by `schema/sample_list.json`). The sample_list entry for each isobaric channel carries up
to four params:

    {
      "id": "<channel-slug>",     // bare sample_list.id, e.g. "channel-tmt126"
      "name": "<source name>",    // verbatim SDRF source name, e.g. "Channel_TMT126"
      "parameters": [
        { "cv_ref": "MS",          "accession": "MS:1002602",
          "name": "sample label",  "value": "TMT126" },               // value = verbatim reagent label
        { "cv_ref": "mzml2mzpeak", "accession": "mzml2mzpeak:reporter-ion-mz",
          "name": "reporter ion m/z", "value": "126.1277" },          // OMITTED when unresolved
        { "cv_ref": "mzml2mzpeak", "accession": "mzml2mzpeak:channel-role",
          "name": "channel role", "value": "sample" },                // sample|pooled|carrier|reference
        { "cv_ref": "UNIMOD",      "accession": "UNIMOD:737",
          "name": "tag modification", "value": "TMT6plex" }           // ONLY when a tag mod is declared
      ]
    }

This models channels as samples (RATIFIED-E), removing the need for a separate `channel_list`.
Only the MS:1002602 *umbrella* is emitted (its `value` is the verbatim reagent label); the specific
reagent child accession (e.g. MS:1002616) is computed internally to resolve the reporter m/z but is
NOT written as a separate param.

#### cv_ref coherence + cv_list declaration (pre-empting the obvious reviewer question)

The two structural attributes (channel-role, reporter-ion m/z) have no canonical PSI-MS accession,
so they use a **project-local `mzml2mzpeak:` namespace** — and each param's `cv_ref` matches its
accession namespace (`"mzml2mzpeak"`, not `"MS"`; the earlier `cv_ref:"MS"` + non-MS-accession
mismatch is fixed). A sample-metadata archive declares every referenced CV (MS + UNIMOD +
mzml2mzpeak) in `metadata.cv_list`, derived from the emitted params so declared == referenced.
The namespaced-identifier choice follows the PSI spring-2026 feedback ("keep namespaced
identifiers — they help detect file mixups"); the spec ask here is to **ratify the
`mzml2mzpeak:channel-role` / `:reporter-ion-mz` tokens as namespaced spec terms** (or mint PSI-MS
accessions), tracked in `docs/cv-requests.md`.

### List-valued ms_run.sample_ref

The run→channel binding uses a list-valued `ms_run.sample_ref` field (P-09). See
`docs/upstream/ms-run-sample-ref-writer-pr.md` for the upstream field specification.

The original `channel_list`/`plex_id`/`channel_set` proposal (former P-04) is WITHDRAWN.
```

## P-05 — Reporter-Ion Quant Auxiliary Array Binding

**Spec mechanism:** Auxiliary Data Arrays (`auxiliary_arrays` list column in `spectra_metadata.parquet`)
**Contract reference:** `docs/mzpeak-extension-contract.md §3.13`
**Source requirements:** QUANT-01, QUANT-02
**Implementing phase:** Phase 35
**Pending CURIEs:** MS:1002302 ("MS:TMT" reporter ion family) tracked in `docs/cv-requests.md`

### Proposed addition to spec `index.md`

```
### Reporter-ion quant auxiliary array binding

Reporter-ion intensities (TMT/iTRAQ per-MS2 peak arrays) are stored as a NonStandardDataArray
named `reporter_intensity` in the spectrum's `auxiliary_arrays` column of `spectra_metadata.parquet`
(MS2-only; absent on MS1). The binding to sample_list channels is carried by a `channel_id` Param
on the array:

    auxiliary_arrays: [
      {
        "name": "reporter_intensity",
        "array": [...],    // Float64 (8-byte LE IEEE-754) intensities, in channel order
        "parameters": [
          {
            "name": "channel_id",
            "value": "sample-1;sample-2"   // bare sample_list.id values, ';'-joined in array order
          }
        ]
      }
    ]

The `channel_id` value is the **bare `sample_list.id`** of each labeled channel (the slugified SDRF
source name, e.g. `sample-1`), semicolon-joined for multi-channel in the same order as the intensity
values — NOT a compound `sample::label` form. This makes peak→channel→sample resolvable without new
base-schema columns.

Ratification: the `channel_id` Param on the `reporter_intensity` aux array is the canonical
reporter-quant binding pattern for isobaric channels in v0.8 (QUANT-01/02, RATIFIED).
```

## P-08 — `metadata.study` Global Study Context

**Spec mechanism:** File-Level Metadata JSON (`metadata` KV, key `"study"`)
**Contract reference:** `docs/mzpeak-extension-contract.md §3.10`
**Source requirements:** SM-05
**Implementing phase:** Phase 32
**Pending CURIEs:** none

### Proposed addition to spec `index.md`

```
### metadata.study — global study context

When a SDRF or ISA bundle is embedded, the file-level `metadata` map carries a `"study"` key
recording global study context:

    {
      "dataset_accession": "<PXD or MTBLS accession or filename-derived>",
      "title": "<study title or empty string>",
      "sample_metadata_ref": "<archive member path to the primary embedded file>",
      "run_sample_binding": {          // OPTIONAL — present only when a filename match succeeded
        "run_id": "<mzML stem>",
        "sample_ids": ["<sample_list.id>", ...],
        "binding_provenance": "phase32_shadow"   // replaced by native ms_run.sample_ref after P-09
      }
    }

The `dataset_accession` is derived from the SDRF filename stem (e.g. `PXD020187.sdrf.tsv` →
`"PXD020187"`) or from the ISA Investigation `Study Identifier` field.

The `sample_metadata_ref` is the deterministic archive member path used to recover the
verbatim embedded file (Q10 RATIFIED: the verbatim blob is the only roundtrip source, not
a projection regeneration).
```

## P-09 — List-Valued `ms_run.sample_ref` Upstream Schema Field

**Spec mechanism:** Upstream `ms_run` schema (HUPO-PSI/mzPeak writer + spec)
**Contract reference:** `docs/mzpeak-extension-contract.md §3.12`; design draft §5.2
**Source requirements:** UPSTREAM-BIND-01
**Implementing phase:** Phase 30b (upstream-first; held for owner authorization)
**See also:** [`docs/upstream/ms-run-sample-ref-writer-pr.md`](./ms-run-sample-ref-writer-pr.md)
**Pending CURIEs:** none (field is JSON schema only, no CV term needed)

### Proposed addition to spec `index.md`

```
### ms_run.sample_ref — list-valued run→sample binding

Add a `sample_ref` field to the `ms_run` schema object:

    "sample_ref": {
      "type": ["array", "string", "null"],
      "items": { "type": "string" },
      "description": "One or more sample_list.id values this run measures. A scalar string
        (single-sample run) or an array of strings (isobaric / fraction×multiplex). When
        absent, the run-sample mapping is unknown (honest default)."
    }

Scalar = 1:1 (single sample); list ≥2 = isobaric or fraction×multiplex. Mirrors mzML's
`<run sampleRef>` but extended to the list-valued case (RATIFIED-F, Q3 ratification).

Until this field is accepted and the writer merges, the `metadata.study.run_sample_binding`
shadow (P-03) is the interim provenance carrier.

Cross-ref: `sample_ref` values are `sample_list.id` values from P-03. For isobaric labeling,
entries in `sample_ref` correspond to the samples-as-channels model (P-04).
```
