## 1. Mandate & core value

**Trigger.** A user converts an mzML file that ships *alongside* a study-metadata document — either a
**SDRF-Proteomics** TSV (PRIDE world) or an **ISA** bundle (ISA-Tab `i_/s_/a_` triple or ISA-JSON;
MetaboLights world). v0.8 makes the converter ingest that document so the **sample ↔ data-file**
relationship and the **global study context** survive into the mzPeak archive.

**Core value (one sentence).** *Given an mzML plus a sibling SDRF or ISA file, pull the global/study
metadata and the sample rows applicable to that mzML into the mzPeak archive — losslessly (verbatim
embed) and queryably (scoped projections with stable join keys) — so the binding survives the
roundtrip and validates against the source ecosystem's reference tools.*

**Why a milestone, not a phase.** The v0.7 plan folded SDRF into a single Phase 27. Adding **ISA** as a
first-class second input (different file topology, different column grammar, different ontologies) plus
the isobaric-channel and reporter-quant work makes this a multi-facet vertical that earns its own
milestone. The keystone is a **format-agnostic internal model** (§3) that both readers populate and a
single emitter consumes — without it, SDRF and ISA would fork the projection logic.

**Non-goals (v0.8).** Computing anything (no reporter deconvolution beyond optional peak picking; no
registration). No auto-discovery of the metadata file (explicit flag only — silent sample-metadata
ingestion is a fidelity risk, consistent with v0.7's stance). No MSI ROI→sample (deferred beyond v1.0
with the rest of the imaging-structure cluster). No non-MS ISA assay types (only MS assays).

## 2. Two input formats — what we are actually parsing

### 2.1 SDRF-Proteomics (the PRIDE/HUPO-PSI flat model)

- **One TSV**, one row per `(sample × data-file × label)`. Columns are ordered, typed by prefix:
  `source name`, `characteristics[...]`, `assay name`, `comment[...]`, `factor value[...]`.
- Ontology values are inline: a cell is either a plain string or `NT=<name>;AC=<accession>;...`
  (e.g. `NT=Xevo G2-S QTof;AC=MS:1002791`).
- Multiplexing: **N rows share one `assay name`, differing in `comment[label]`** (`TMT126`…).
- File binding: `comment[data file]` (and/or `comment[file uri]`) names the raw/processed file.
- Governance: HUPO-PSI / `bigbio/proteomics-sample-metadata` (spec v1.1.0); reference validator
  `sdrf-pipelines`.

### 2.2 ISA (the MetaboLights/normalized model)

ISA is **normalized across files**, not flat:

- **`i_Investigation.txt`** — *global*: title, description, contacts, publications, **Ontology Source
  References** (the CV registry: EFO, NCBITaxon, CHMO, MSIO, …), **Study Factors**, **Study Protocols**,
  **Study Assays**, **Study Design Descriptors**. → mzPeak **file-level metadata**.
- **`s_*.txt`** (Study file) — `Source Name → Characteristics[...] → Protocol REF → Sample Name`.
  Maps biological sources to samples. → **sample_list**.
- **`a_*.txt`** (Assay file) — `Sample Name → Protocol REF → Parameter Value[...] →
  (Labeled Extract Name / Label) → MS Assay Name → Raw Spectral Data File / Derived Spectral Data File`.
  Links a sample to the actual data file. → **assay_ref / run binding / (channel)**.
- ISA carries CV linkage **out-of-band** via paired columns: a value column followed by
  `Term Source REF` + `Term Accession Number`, with the source defined in the Investigation's Ontology
  Source References. (SDRF inlines the same info as `NT=/AC=`.)
- **ISA-JSON** is the same object model serialized as nested JSON (`investigation → studies[] →
  {materials.sources, materials.samples, processSequence, assays[]}`).
- Governance: ISA-Tools / MetaboLights; reference tooling `isa-api` (Python `isatools`),
  `linkml`/`mars` adjacent. Metabolomics is overwhelmingly **label-free** → channels rarely apply.

### 2.3 The unifying insight

Both formats answer the same three questions, at three scopes:

| Question | SDRF source | ISA source | mzPeak home |
|---|---|---|---|
| *What is the study?* (global) | repeated `comment[*]`/`factor value` headers + dataset accession | `i_Investigation.txt` | file-level `metadata` KV |
| *What are the samples?* | distinct `source name` + `characteristics[*]` | `s_*.txt` Source/Sample + `Characteristics[*]` | `sample_list` |
| *Which sample(s) did THIS file measure, and how?* | rows whose `comment[data file]` = this file | `a_*.txt` rows whose `Raw/Derived Spectral Data File` = this file | list-valued `ms_run.sample_ref` → labeled `sample_list` entries (channels = samples, [RATIFIED-E]) |

⇒ A single normalized model (§3) with a single emitter (§5). Format-specific logic lives **only** in
the two readers (§4).

## 3. Keystone: the unified internal model (`StudyMetadata`)

A format-agnostic Rust representation that both readers produce and the emitter consumes. CV handling
is centralized in one type (`TypedValue`) so the cvParam/userParam decision (Cornerstone A) is made in
exactly one place.

```rust
/// One normalized study-metadata document, already sliced to THIS mzML file.
struct StudyMetadata {
    source_format: SourceFormat,          // Sdrf | IsaTab | IsaJson
    global: GlobalContext,                // investigation/study-level (file-level metadata)
    samples: Vec<Sample>,                 // distinct biological sources/samples referenced by this file
    assays: Vec<Assay>,                   // assay rows binding sample(s) -> this data file
    factor_levels: Vec<TypedValue>,       // THIS file's factor-value levels (from study AND assay files — R1-H4)
    channels: Vec<Channel>,               // isobaric channels (empty for label-free / SILAC / metabolomics)
    verbatim: VerbatimBundle,             // the raw source bytes (lossless anchor) — see §5.1
    diagnostics: Vec<Diagnostic>,         // warnings/notes surfaced to the user + recorded in metadata
}

/// OWN verbatim-string CURIE — NOT mzdata::CURIE (which is a CLOSED CV enum +
/// integer accession; it silently collapses NCBITaxon/Unimod/Cellosaurus/CHMO/MSIO
/// to `Unknown`, breaking the reversibility invariant — R3-H1). Strings, verbatim.
struct SourceCurie { prefix: String, accession: String, label: Option<String> }

struct TypedValue {
    column: String,                       // EXACT source column header, e.g. "characteristics[organism]"
    value: String,                        // lexical cell value, verbatim
    accession: Option<SourceCurie>,       // from SDRF AC= or ISA Term Accession Number, if present
    term_source: Option<String>,          // ISA Term Source REF / SDRF source
    unit: Option<SourceCurie>,            // unit accession if the column carries one
    is_na: bool,                          // reserved sentinel (not available/applicable, anonymized) — R1-M5
    // Long-tail SDRF cell tokens that don't fit the slots above (MT/TA/PP/CT/PS/…):
    // e.g. comment[modification parameters] = NT=Oxidation;AC=UNIMOD:35;MT=Variable;TA=M;PP=Anywhere
    extra: Vec<(String, String)>,         // verbatim key=value pairs — preserves modification semantics (R1-H1)
}

struct Sample { id: String,              // SDRF `source name` / ISA Source(or Sample) Name = sample_list key
               name: String, characteristics: Vec<TypedValue> }

struct Assay { id: String,               // SDRF `assay name` / ISA `MS Assay Name`
              sample_refs: Vec<String>,  // -> Sample.id
              data_files: Vec<String>,   // matched against this mzML
              parameters: Vec<TypedValue>, // Protocol REF + Parameter Value[*] (instrument, chroma, …)
              label: Option<String> }    // comment[label] / ISA Label — drives channel resolution

// [RATIFIED-E] `Channel` is a PARSE-time struct only. The emitter writes each one as a labeled
// `sample_list` entry — `label` → a `sample label` cvParam (MS:1002602), plus reporter_mz / role /
// tag_modification as params — bound via the list-valued `ms_run.sample_ref`. There is NO `channel_list`.
struct Channel {                          // ISOBARIC only (Q4/Q5) — emitted AS labeled samples
    id: String, label: TypedValue,        // comment[label] -> MS:1002602 sample-label child (e.g. TMT126)
    reporter_mz: Option<f64>,             // None when unresolved (TMTpro 16/18-plex gap) — never a sentinel f64 (R1-M4)
    reporter_mz_source: String,           // reagent-table | vendor-method | unresolved — SOURCE RECORDED (Q8)
    tag_modification: Option<TypedValue>, // Unimod (TMT6plex = UNIMOD:737)
    sample_refs: Vec<String>, pool_member_refs: Vec<String>,
    role: ChannelRole,                    // Experimental|Reference|Carrier|Norm|Empty (Q5)
    sdrf_row_ref: Option<String>,         // "source name :: assay name :: comment[label]" (Q1/Q10)
}
```

**Invariant:** `verbatim` is the only thing the roundtrip re-serves. Everything else
(`samples/assays/channels/factor_levels`) is a *projection* — an index into the verbatim rows, never a
regeneration source (Q10). This is the load-bearing rule that keeps us lossless without having to make
the projection perfectly invertible.

## 4. The two readers (the only format-specific code)

### 4.1 SDRF reader

1. Parse the TSV with `csv`: `delimiter(b'\t')`, `flexible(true)` (rows are ragged), and **`quoting(false)`**
   — SDRF cells legitimately contain `;` and `=`; RFC-4180 `"` quoting would mis-split
   `characteristics[…]` cells (R3-M3). Header drives column typing by prefix.
2. Parse each cell on the real SDRF key grammar (R1-H1): the token set is
   `NT, AC, MT, TA, PP, CT, QY, PS, SP, CN, CV, CL, MH, ML, VV` (there is **no** `TT`). `NT`→`value`/label,
   `AC`→`accession`, units→`unit`; **all other tokens preserved verbatim in `TypedValue.extra`** so that
   `comment[modification parameters] = NT=Oxidation;AC=UNIMOD:35;MT=Variable;TA=M;PP=Anywhere` keeps its
   fixed/variable status (`MT`), target residue (`TA`), and position (`PP`). Reserved sentinels
   (`not available`/`not applicable`/`anonymized`) set `is_na` (R1-M5); plain cells → `value` only.
3. **File-row matching:** keep rows whose **`comment[data file]`** (the canonical, required binding
   column — `comment[file uri]` is an *optional* secondary hint; `associated file uri` is not standard,
   R1-M1) matches this mzML by **path-stripped basename** across known sibling extensions
   (`.raw`/`.d`/`.wiff`/`.mzML`/`.mzml` — SDRF often names the *raw* file; fixture values are
   path-prefixed like `FILES/QC01.mzML`, so strip the path, R3). Record the matched name + a diagnostic.
4. Build `samples` from distinct `source name` (mapping the four reserved sentinels to `is_na`, and
   `pooled`/`characteristics[pooled sample]` to the pooled flag); `assays` from distinct `assay name`;
   `factor_levels` from this file's `factor value[*]`. **Channel trigger:** isobaric rows only — a row
   whose `comment[label]` is in the TMT/iTRAQ label set. **Explicitly exclude** the non-isobaric label
   sentinels `label free sample` and `SILAC light|medium|heavy` from the channel path (R1-H3); SILAC
   light/medium/heavy assignment is recorded as run/assay metadata + a `Diagnostic` ("SILAC label
   preserved in verbatim only" — it is MS1 quant, no `channel_list`).
5. **Role derivation (R1-H2):** carrier/reference roles come from the **dedicated columns**
   `comment[carrier channel]` / `comment[reference channel]` whose *value is the channel label* — match
   each row's `comment[label]` against them. Pooled via `characteristics[biological replicate]==pooled`
   / `characteristics[pooled sample]=SN=…`. (`characteristics[sample type]` is a non-standard fallback
   only, not the primary source.)
6. `verbatim` = the matched rows **plus the header** (a valid sub-SDRF) — and optionally the whole TSV
   (Cornerstone A / Q1 precedence; see §5.1).

### 4.2 ISA reader (Tab + JSON)

1. **ISA-Tab:** locate the bundle (a directory, or a `.zip`, or the `i_*.txt` path → its siblings).
   Parse `i_Investigation.txt` (section-keyed, tab-delimited blocks) → `global` + the Ontology Source
   Reference registry (resolves `Term Source REF` → real CV) + the Study Factor/Protocol definitions.
2. Parse `s_*.txt` → `samples` (Source/Sample Name + `Characteristics[*]` with their paired
   `Term Source REF`/`Term Accession Number`).
3. Parse `a_*.txt` → `assays`; **file-row matching** on `Raw Spectral Data File` /
   `Derived Spectral Data File` (also tolerate `Acquisition Parameter Data File` + `MS Assay Name`,
   R1-M2). Join assay rows → **Sample Name → Source Name** to pull each measured sample's
   characteristics; note the join may fan out through intermediate `Extract Name` / `Labeled Extract
   Name` + `Label` nodes (the ISA analog of isobaric multiplexing — 1 Sample : N labeled extracts,
   R1-M3; modeled only if a labeled ISA assay is encountered, else degrade to verbatim + diagnostic).
4. **Harvest `Factor Value[...]` from BOTH `s_*.txt` and `a_*.txt`** (ISA permits factor values at
   study *and* assay scope; assay-scoped ones are the most likely per-run, R1-H4) and merge by the
   Sample Name join.
5. **ISA-JSON:** ISA-JSON has its *own* nested schema (material nodes with `@id`, process sequences),
   so it needs its **own `Deserialize` layer + `@id` reference resolution**, then a projection into
   `StudyMetadata` — exactly as ISA-Tab needs a projection (R3-M4). Net: **three parse front-ends**
   (SDRF cells · ISA-Tab blocks · ISA-JSON nodes) feeding **one** target model — not one deserialize.
6. `verbatim` = the **whole ISA bundle** (investigation + the relevant study + the relevant assay
   files, or the ISA-JSON), because ISA is normalized — a single assay file is meaningless without its
   investigation. (This is a real divergence from SDRF; see Risk R5.)

**Shared post-conditions:** both readers emit a populated `StudyMetadata` with identical projection
semantics; all CV decisions deferred to `TypedValue`; all "couldn't map" cases produce a `Diagnostic`,
never a silent drop.

## 5. The emitter — what lands in the mzPeak archive

> **Prerequisite refactor (R3-H3 — the real cost of Phase 31).** SDRF/ISA accompany *proteomics
> `.mzML`*, which routes to **`convert_mzml` (`src/write/mzml.rs`)**, not the imaging converter. Today
> `convert_mzml` finalizes via the high-level `writer.finish()` — it never opens the `ZipArchiveWriter`,
> never calls `add_index_metadata`, and has **no** `Other`-member insertion point. The "index-written-
> last" seam the rest of this section relies on exists **only** in the imaging `src/write/convert.rs`.
> So Phase 31 must first refactor `convert_mzml`'s one-line `finish()` into the lower-level seam
> `let zip = writer.finish_parquet()?; zip.add_index_metadata(…); /* typed-member embeds */ zip.finish()?;`
> mirroring imaging. Every embed/KV-JSON write in §5.1–§5.2 hangs off that seam. Plus the whole CLI flag
> layer (`--sdrf`/`--isa`/`--embed-full-*`/`--validate-sample-metadata`/`--reconstruct-*`) is net-new
> (`Cli` has none today, R3-H4).

### 5.1 Verbatim embed (the lossless anchor) — local, no upstream dep

- Add the source document(s) as a ZIP member with a **deterministic name**
  (`sample_metadata/sdrf.tsv`, or `sample_metadata/isa/{i_…,s_…,a_…}.txt` / `isa.json`). The convenience
  helpers `start_other`/`add_file_from_read` **hardcode** `Other("other")` — so to get a *typed* member
  use **`start_for_entry(FileEntry::new(name, EntityType::Other("sample-metadata"), DataKind::Other("sdrf"|"isa")))`**
  + a manual byte-copy loop (R2-H1, R3-H2).
- **`entity_type`/`data_kind` are descriptive-only open-enum strings** — they serialize and round-trip
  but **no reader dispatches on them** (`FileEntry::archive_type()` maps any `Other(_)` → `Other`).
  Retrieval is therefore **by the deterministic archive name recorded in the index block**, exactly the
  shipped imaging-TIFF precedent (`metadata.imaging.images[].archive_path`) — not by facet (R2-H1/L1).
- **Embed scope + provenance (Q1 precedence, R4-M4):** default embeds **the file's applicable rows +
  header** (a valid sub-document) and records, in the index.json `metadata` map,
  `metadata.sample_metadata = {dataset_accession, source_uri, format, embed_scope:
  "applicable_rows"|"full", precedence: "repo_wins", sha256, retrieved_at}` (the hash + timestamp guard
  against the embedded snapshot going stale vs. a later repo correction). A `--embed-full-sdrf` /
  `--embed-full-isa` opt-in embeds the entire source. The repo document stays authoritative.

### 5.2 Projections (query surface) — split local vs upstream (Cornerstones C & D)

**One carrier for all KV projections:** the **`mzpeak_index.json` `metadata` map** — a
`HashMap<String, serde_json::Value>` with `additionalProperties: true`, written via
`add_index_metadata(key, val)` (the exact mechanism the shipped imaging block uses). This is NOT a
`data_kind: "metadata"` ZIP member, and NOT the Parquet-footer KV — those are different stores (R2-H2).
Caveat: the index.json `metadata` map is **not exercised by any shipped example**, so this is
spec-*permitted* (schema-open) but un-proven ground, not "proven."

> **[RATIFIED-G] Lean posture.** The verbatim blob (§5.1) is the full-fidelity anchor; the projections
> below are a **minimal** query surface, not a re-serialization of SDRF. The rows marked *deferred* hold
> their fidelity in the blob and are pushed to ≥v0.9 (JK: *"a reader shouldn't have to be an SDRF writer"*).

| Projection | Carrier | Status |
|---|---|---|
| Global study context | `metadata.study` (index.json map) | **Local — minimal** (accession, title, back-ref; not every header) |
| `sample_list` entries (one per `source name`; **and one per isobaric channel** — [RATIFIED-E]) | reuse **`sample.json`** (id/name/parameters) | **Local.** Each entry carries id + name; **isobaric** entries also carry a `sample label` cvParam (**MS:1002602**) + reporter-m/z + role + `tag_modification` (Unimod) as params. Full `characteristics→Param` shaping is **demoted** (blob holds it). |
| isobaric **channels** | *(no new construct)* | **[RATIFIED-E] Samples-as-channels** — channels ARE labeled `sample_list` entries (above). The `channel_list` is **dropped**; MS:1002602 + list-valued `sample_ref` already model it (mzML precedent). |
| **run → sample binding** | **list-valued `ms_run.sample_ref` schema field (UPSTREAM)** | **[RATIFIED-C/F] Upstream-first, LIST-valued** — added to HUPO-PSI/mzPeak + spec (a *list* of sample refs, so multiplexing falls out of it — JK), merged, *then* emitted + queryable. Binding phase gates on the merge; a `metadata.study.run_sample_binding` index.json key is the interim provenance shadow. No `sample_ref` ⇒ samples mixed (JK's default). |
| `factor_values` (this file's levels) | — | **[RATIFIED-G] DEFERRED ≥v0.9** — lives in the verbatim blob; not natively projected in v0.8. |
| `comment[…]` scope decomposition | — | **[RATIFIED-G] DEFERRED ≥v0.9** — verbatim blob holds all `comment[*]` columns. |
| **per-spectrum `assay_ref`** | — | **DEFERRED ≥v0.9** (new arrow column + hot loop + PIX-01 coupling). v0.8 binding is **run-level** (Cornerstone D). |
| reporter-quant (`channel_id` on auxiliary array) | `auxiliary_array.parameters` | **Local but optional/gated** — read-back *likely-to-fail* third-party (aux arrays = Arrow struct columns; R can't decode; Python null-fill name-gated — R2-M3); own-reader spike. |

> **[RATIFIED-C] Native queryability, at the cost of merge latency.** Choosing upstream-first means the
> run↔sample join is a *real schema field readers resolve*, not a KV shadow — §1's "queryably" promise
> is met in full. The trade is that the binding phases (Phase 33's run-binding, downstream) are **gated
> on the upstream `ms_run.sample_ref` PR merging**, exactly as v0.7 Phase 29 is gated on chunk_series.
> Mitigation: the PR is prepared and opened EARLY (Phase 30b) so its merge clock overlaps every
> non-blocked phase (verbatim embed, readers, sample_list, channels).

**[RATIFIED-C] Design stance / de-vendor reconciliation.** No local writer fork is ever carried. The
`ms_run.sample_ref` field lands **upstream-first**; since the un-forked writer then already contains it,
v0.7 Phase 29's "zero fork divergence" and v0.8's native binding are *mutually consistent* — the
collision (R4-H2) dissolves. Everything else (verbatim `Other` members, index.json KV map, `sample_list`,
aux arrays) still uses existing mechanisms with no upstream wait. This keeps the "build local where you
can, upstream where you must, batch the spec proposal" discipline intact.

### 5.3 Round-trip & validation (Q10)

- Roundtrip = re-serve the embedded verbatim document byte-for-byte. The `--reconstruct-sdrf` /
  `--reconstruct-isa` reverse path extracts the member; it does **not** regenerate from projections.
- **External validation gate (Cornerstone B):** optional `--validate-sample-metadata` shells out to the
  reference validator (`sdrf-pipelines` for SDRF; `isa-api`/`linkml` for ISA) when present, as a
  non-blocking oracle. Fixtures: label-free SDRF (MTBLS1129-style), TMT 10-plex SDRF (PXD011799), and a
  true ISA-Tab metabolomics bundle (a MetaboLights `i_/s_/a_` triple — to be added to
  `data/sdrf-examples/` as a real ISA fixture, since MTBLS1129 here is SDRF-form, not native ISA).

## 6. Topology coverage (the cases that must work)

| Topology | sample : file | binding | formats |
|---|---|---|---|
| label-free | 1 : 1 | `ms_run.sample_ref` → one `sample_list` entry; no labels | SDRF + ISA |
| fractionation | 1 sample : N files | same sample id referenced across files | SDRF + ISA |
| multiplex (TMT/iTRAQ) | **N : 1** | list-valued `ms_run.sample_ref` → N labeled `sample_list` entries (MS:1002602 sample-label cvParam) [RATIFIED-E] | SDRF (ISA rare) |
| fraction × multiplex | N × M | N labeled samples per run × shared sample ids across fraction files | SDRF |
| pooled / carrier / reference | N→1 channel | `sample_refs` + `pool_member_refs`; `role` derived | SDRF |
| metabolomics (MetaboLights) | 1 : 1, label-free | ISA assay row → sample; CHMO/MSIO CVs | **ISA** |

The label-free 1:1 case is the breadth target, but the **true de-risking MVP is thinner still**:
**verbatim embed + byte-identical roundtrip alone** (Phase 31) — lossless, demoable, upstream-
independent — *before* any projection/query surface (R4-H4). Projections (sample_list, run binding)
layer on in Phase 32.

## 7. Cornerstone decisions (for user ratification — §11 discussion)

> These three are the architectural forks the design leaves open on purpose; each changes downstream
> work. Recommendations are first.

### Cornerstone A — CV / OBO integration depth

How do we treat the ontology accessions (EFO, PSI-MS, NCBITaxon, Unimod, Cellosaurus, CHMO, MSIO,
PRIDE) that SDRF inlines and ISA carries out-of-band?

- **A1 (recommended) — Passthrough + structure-only validation.** Emit a `cvParam` when the source row
  carries an accession (verbatim CURIE + label), else a `userParam` whose name is the *exact* source
  column (reversible). We validate **shape** (is `AC=` a well-formed CURIE? does ISA's `Term Source REF`
  resolve to an Ontology Source Reference?), not **existence** (we don't fetch the ontology). Zero new
  deps, fully reversible, honest. Real semantic validation is delegated to the external tools
  (Cornerstone B).
- **A2 — Offline OBO bundle.** Vendor curated `.obo` for the core set and resolve/validate label↔accession
  at convert time. Real validation + label normalization, but EFO alone is huge, the bundle rots, and it
  bloats the binary. Heavy.
- **A3 — Online OLS resolution.** Resolve via EBI OLS at convert time. No bundle, but adds a network
  dependency to a converter (offline/repro hostile). Reject for the core path.

Cross-cuts: the **structural CV terms** mzPeak itself needs (sample-metadata entity, channel, role,
assay_ref) are minted in **PSI-MS** regardless of A1/A2/A3 — that's Cornerstone C, not this one.

### Cornerstone B — SDRF/ISA reader-writer implementation

- **B1 (recommended) — Pure-Rust readers + optional external validator oracle.** Parse SDRF (`csv`) and
  ISA (hand parser + serde_json) in-process; keep the all-Rust core (CLAUDE.md explicitly avoids a
  Python↔Rust boundary). When the user passes `--validate-sample-metadata` *and* the reference tool is
  on PATH, shell out to it as a **non-blocking** correctness oracle in CI/fixtures. We never depend on
  Python at runtime for the conversion itself.
- **B2 — Python sidecar for parse+validate.** Call `sdrf-pipelines` / `isatools` to parse and hand us
  normalized JSON. Authoritative parsing, but bakes a Python runtime into a Rust CLI — deployment
  friction, contradicts the project's stated architecture.
- **B3 — Rust SDRF only, defer ISA.** Ship SDRF in v0.8, push ISA to v0.9. Smaller, but abandons the
  unifying-model payoff and the user's explicit ISA ask.

New crate cost of B1: `csv` (already anticipated in v0.7) + nothing else for ISA-Tab (hand parser) +
`serde_json` (already a dep) for ISA-JSON.

### Cornerstone C — Upstream changes (mzpeak_prototyping / mzdata / spec)

What actually requires an upstream change vs. fits existing mechanisms:

- **mzdata (reader): essentially none.** SDRF/ISA are sibling files we read directly — mzdata is not in
  that path. *Possible optional* item: surface the mzML `<sampleList>` if present so we can cross-check
  an in-mzML sample id against the SDRF `source name`. Low value; **no mzdata change in v0.8**.
- **mzpeak_prototyping (writer) — zero local patches in v0.8.** Note there is no `ms_run` *struct* to
  add a field to; the run is itself a KV-JSON blob serialized from mzdata (R3-M2). The two genuine
  schema fields (`ms_run.sample_ref`, per-spectrum `assay_ref` column) would each **re-fork the writer
  that v0.7 Phase 29 is de-vendoring** — you cannot hold "zero fork divergence" (DVN-01/02) *and* carry
  a `sample_ref` patch (R4-H2). So:
  - **[RATIFIED] Upstream-first (the owner's choice).** Add `ms_run.sample_ref` to HUPO-PSI/mzPeak +
    spec, merge it, *then* build v0.8 native binding against the un-forked writer. **No local fork ever
    carried** → the Phase 29 de-vendor collision dissolves (the un-forked writer already has the field).
    Cost = merge latency; mitigated by opening the PR EARLY (Phase 30b) and front-loading non-blocked
    phases. PR submission is owner-gated (push-policy: HUPO-PSI is outside `okohlbacher` → explicit
    interactive authorization required).
  - *(Not chosen: KV-JSON-only-no-upstream — would leave the join un-queryable; re-fork-now — collides
    with Phase 29.)*
- **Spec (HUPO-PSI/mzPeak-specification):** mint the structural terms from the open-questions doc §B
  (sample-metadata entity / sdrf+isa data-kind, isobaric channel, channel role enum, reporter-ion m/z,
  assay/sample reference, SDRF-row reference) and ratify Q1–Q10. Submitted as **one batch** at the end
  of v0.8. **NB (R4-H1):** v0.7's SPEC-02 batch must be **re-scoped to imaging/IMS terms only** so the
  sample-metadata + channel terms aren't double-owned by both milestones (see §10).

### Cornerstone D — Binding granularity: run-level vs per-spectrum *(promoted from a §5.2 footnote — R4-M1)*

The single decision that most changes downstream cost. Does v0.8 bind sample/assay at **run level**
(cheap, local, KV-JSON) or **per-spectrum** (a new Arrow column on the spectrum/scan table)?

- **[RATIFIED] D1 — run-level only.** Every spectrum in a run shares the run's sample/channel binding
  (true for the SDRF/ISA topologies in §6 — multiplex differs by *reporter channel within* an MS2, not
  by *which run*). The single upstream field needed is therefore the run-level `ms_run.sample_ref`
  (Cornerstone C), keeping the upstream ask minimal and mergeable. Per-spectrum `assay_ref` is
  **deferred to ≥v0.9**, explicitly tied to the post-v1.0 PIX-01 scan-compound-key work.
- *(Not chosen: per-spectrum now — a pinned-arrow column + hot-loop touch + a larger upstream surface;
  wrong altitude for v0.8.)*

## 12. Risk register

| ID | Risk | Mitigation |
|---|---|---|
| R1 | CV explosion — characteristics with no accession degrade to free text, losing queryability | Accept (A1): userParam keyed by exact column = reversible; validation delegated to external tool |
| R2 | Per-spectrum `assay_ref` needs an upstream schema field we don't control | KV-JSON run-level fallback (Cornerstone C2); per-spectrum deferred if upstream stalls |
