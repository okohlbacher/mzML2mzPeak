<objective>
Establish the Phase 2 library crate and define the data contracts that the rest of the
read layer (Plan 03 streaming reader) and Phase 4's writer will consume. This is the
interface-first skeleton plan: it creates `src/lib.rs`, wires the `[lib]` target in
`Cargo.toml`, declares the `read` and `integrity` module seams, and defines the
per-spectrum record type and run-level provenance type that downstream plans implement
against.

The central contract decision (CRITICAL, from the start-of-phase review and spec v0.3 §8
L1 "bit-for-bit"): the record must PRESERVE the source dtype of each numeric axis, not
coerce it. imzML declares each array's dtype independently (HR2MSI: m/z `MS:1000523`
64-bit, intensity `MS:1000521` 32-bit; the continuous fixture: m/z `MS:1000521` 32-bit).
mzdata's convenience accessors `BinaryArrayMap::mzs()`/`intensities()` COERCE — `mzs()`
widens any m/z to `f64`, `intensities()` narrows any intensity to `f32` — which silently
destroys the source representation and makes L1 round-trip impossible. Therefore each axis
is modeled as a `NumArray` enum carrying the values AT their decoded dtype.

Purpose: downstream plans (integrity preflight, streaming reader, future writer) must
build against fixed type contracts rather than rediscovering field shapes. Defining the
record type and run provenance first prevents a scavenger hunt and locks the coordinate
semantics (SPA-02), the dtype-preservation contract (IN-04), and carried metadata
(IN-05 representation flag, IN-06 ms_level + id) in one place.

Output: a compiling library crate with `ImagingSpectrum`, `NumArray`, `RunProvenance`,
`Representation`, and `StorageMode` types, the `read` module surface, and an `integrity`
module declaration that Plan 02-02 fills.
</objective>

<dtype_facts>
- The imzML IBD read path (vendor/mzdata/src/io/imzml/reader.rs ~line 991) supports
  ONLY `NoCompression`/`Decoded` arrays; any other compression returns an Err. Phase 2 is
  therefore scoped to UNCOMPRESSED .ibd (IN-04, ROADMAP criterion 1). The record type does
  not need to model compression — arrays arrive already decoded at their native dtype.
- After decode, `DataArray.dtype` is the array's SOURCE dtype (Float32 or Float64 for the
  m/z and intensity axes in our fixtures). Reading values at that exact dtype (to_f32 when
  Float32, to_f64 when Float64) preserves the bytes; calling to_f64 on a Float32 array
  WIDENS (lossy for L1) and calling to_f32 on a Float64 array NARROWS (lossy). This is the
  whole reason for the NumArray enum.
</dtype_facts>
