<objective>
Build the production streaming read layer: an `ImagingReader` that opens an .imzML/.ibd
pair (running the Plan 02-02 integrity preflight FIRST and refusing to proceed on
failure), auto-detects the storage mode from the file-level data_mode CV param, and yields
one fully-populated `ImagingSpectrum` at a time via the `Iterator` trait — never collecting
all spectra, so the 34,840-spectrum / 815MB dataset streams under bounded memory. Each
numeric axis is decoded AT its imzML-declared source dtype into the dtype-preserving
`NumArray` enum from Plan 02-01 (NOT coerced via `mzs()`/`intensities()`), and a
decode/IO failure surfaces as `Err` rather than a silently short stream. This is the layer
Phase 4's writer consumes.

Purpose: turn the proven spike read path (spike_coords.rs) into a reusable library API that
delivers per-pixel coordinates (SPA-01), dtype-preserving decoded m/z+intensity arrays
(IN-04), storage-mode detection (IN-03), and carried per-spectrum metadata (IN-06), for
both processed (IN-01) and continuous (IN-02) modes, bounded in memory (IN-08).

Output: `src/read/stream.rs` with `ImagingReader`, the `pub mod stream;` wiring in
`src/read/mod.rs`, a small committed `Example_Processed` fixture, and integration tests:

<dtype_extraction>
For each axis, read the DataArray and decode AT its declared dtype into a NumArray variant —
NEVER coerce via map.mzs()/intensities():

  let arrays = spec.raw_arrays().ok_or(ReadError::NoArrays { index })?;
  let mz_da = arrays.get(&ArrayType::MZArray).ok_or(ReadError::NoArrays { index })?;
  let mz = match mz_da.dtype {
      BinaryDataArrayType::Float32 => NumArray::F32(mz_da.to_f32().map_err(decode err)? .into_owned()),
      BinaryDataArrayType::Float64 => NumArray::F64(mz_da.to_f64().map_err(decode err)? .into_owned()),
      other => return Err(ReadError::UnsupportedDtype { index, dtype: other }),  // imaging m/z is f32/f64 only in scope
  };
  // identical pattern for IntensityArray.

Calling to_f32() on a Float32 array (or to_f64() on a Float64 array) does NOT widen/narrow —
it returns the values at their native dtype, so the NumArray carries the exact source
representation (IN-04, L1 bit-for-bit). Int dtypes are out of scope for Phase 2 imaging
axes; return UnsupportedDtype if encountered (a clear error, not a silent coercion).
</dtype_extraction>

<decode_error_handling>
CRITICAL (review finding): mzdata's reader `Iterator::next()` returns `None` BOTH on a
clean end-of-run AND when an underlying parse/IO error occurs — so a malformed
offset/length in a truncated/corrupt .ibd can become a SILENT short stream (early EOF)
rather than an error. The ImagingReader MUST distinguish these. While reading reader.rs,
determine the most reliable mechanism and use it (in priority order):
  1. If the reader exposes a fallible read (e.g. `read_next`/`read_into` returning
     Result, or an accessor for the last parser error/state), call THAT and map a parse/IO
     error to `ReadError::Decode { index, source }` instead of treating it as end-of-run.
  2. If only `next() -> Option<Spectrum>` is available, cross-check completion against an
     expected count when known (e.g. the imzML's declared spectrum count / spectrumList
     `count` attribute) so a short stream is detected; if the count is unknown, at minimum
     surface the reader's error state if any is queryable.
The Decode-error test below (truncated-.ibd fixture) must FAIL the iteration with an Err,
not yield a silently truncated set of spectra. If, after reading the source, mzdata truly
exposes no error signal at all, document the exact limitation in the SUMMARY and implement
the expected-count cross-check as the surfacing mechanism — do NOT ship a reader that
cannot tell truncation from completion.
</decode_error_handling>
