- UUID BYTE ORDER (corrected per review — primary path is RFC-4122):
  The imzML data-structure spec (https://www.ms-imaging.org/imzml/data-structure/) states the .ibd's
  first 16 bytes are an RFC-4122 / network-order (big-endian, byte-for-byte) UUID equal to the textual
  IMS:1000080 hex. This is how pyimzML reads it. The verifier MUST therefore compare the first 16 bytes
  byte-for-byte against the textual UUID's hex (big-endian): byte[0]=0xC7, byte[1]=0x82, byte[2]=0x23,
  byte[3]=0x30, byte[4]=0xF1, byte[5]=0xA8, byte[6]=0x4D, byte[7]=0x11, byte[8]=0xAD, byte[9]=0x30,
  byte[10..16]=0x50 0x4B 0x30 0xB3 0x37 0x22. The PRIMARY acceptance is the RFC-4122 match.
  Only IF the RFC-4122 comparison FAILS should the verifier additionally report a .NET mixed-endian
  interpretation (Data1 u32 LE, Data2 u16 LE, Data3 u16 LE, Data4 8 bytes as-is) as a DIAGNOSTIC to
  help the operator understand a non-compliant file — never as the primary/required path.

- SHA-1 SCOPE: the IMS:1000091 SHA-1 is computed over the ENTIRE .ibd file, INCLUDING the first 16
  UUID bytes (no offset, no exclusion). Stream the whole file from byte 0 to EOF.
