# Quick Task 260609-8wo — Reconcile directory-name vs instrument-model mismatches

## Task

Two mzML-corpus directories carry names that disagree with the true instrument model.
Verify each against the **in-file** `<instrumentConfiguration>` / `<softwareList>` cvParams
(ground truth), pick the least-disruptive *correct* fix, and propagate the correction across
docs, READMEs, knowledge notes, and scripts.

## Verification (in-file ground truth — both files present locally)

### 1. `data/mzML-examples/agilent-qtof/` (Zenodo 18502866, `MRM-standmix-5.mzML`)

In-file evidence:
- `referenceableParamGroup`: `MS:1000490 "Agilent instrument model"` (value empty) +
  `userParam name="instrument model" value="TandemQuadrupole"`.
- `instrumentConfiguration`: **three `MS:1000081 quadrupole` analyzers** (order 2/3/4) + electron
  multiplier detector → a **triple quadrupole (QqQ)**, not a Q-TOF.
- `softwareList`: MassHunter Data Acquisition 7.0 + ProteoWizard.
- Content: **0 spectra / 138 chromatograms** (dMRM, chromatogram-only) — matches the archive's
  "dynamic MRM" description.

Conclusion: the directory label `agilent-qtof` is a **misnomer** — the instrument is a triple quad.
The specific model number **6490** is not in the file (file says only `TandemQuadrupole`); it comes
from the Zenodo deposit metadata.

### 2. `data/mzML-examples/waters-xevo-g2s-qtof/` (MetaboLights MTBLS1129, `QC01.mzML`)

In-file evidence:
- `instrumentConfiguration`: `MS:1000126 "Waters instrument model"` with **value empty** — the file
  does **not** encode a specific model.
- `softwareList`: MassLynx 4.1 + ProteoWizard. Content: 2281 spectra / 1 chromatogram → a QTof run.

Conclusion: the QTof axis is correct. The file itself does **not** distinguish G2-S vs G2-XS; the
only authority for the sub-model is the MetaboLights record, which names a **Xevo G2-XS QTof**. The
directory label `…-g2s-…` is off by one sub-model letter.

## Decision — Option (b): KEEP both directory names, add clear correction notes

Rationale (least-disruptive correct option):
1. **`data/` is git-ignored** and the StackIT S3 bucket already holds objects under the existing
   `mzML-examples/agilent-qtof/` and `mzML-examples/waters-xevo-g2s-qtof/` prefixes
   (`scripts/push-data-stackit.sh` syncs by directory name). Renaming locally orphans the uploaded
   S3 objects and forces a re-upload + index rebuild.
2. **Agilent rename collision:** the obvious correct name (`agilent-6490-triplequad`) is **already
   taken** by a separate corpus entry (PRIDE PXD041762). Renaming `agilent-qtof` to any 6490-QqQ
   variant collides or creates a confusing near-duplicate.
3. **Waters:** the in-file model field is empty (file does not encode G2-S vs G2-XS); the QTof axis
   the corpus actually tests is correct; the slug is also cross-referenced as the SDRF fixture
   (`sdrf-examples/MTBLS1129`). A one-letter sub-model rename ripples far for no schema benefit.

`make-s3-index.py` (groups by `mzML-examples`, no per-dir hardcode), `push-data-stackit.sh` (globs
`data/mzML-examples/*/`), and `upload-demo-stackit.sh` (no refs) require **no changes** under option (b).
